内存对齐细节

2026-05-272 min read (651 words)
目录

补充一些平时可能会疏忽的+有趣的对齐细节

对于现代x64处理器，不跨cache line的非对齐访问通常已经不是很大的问题，这个范畴内对齐与否通常只有μop级别的差距；需要注意的是手动内存管理的随意非对齐问题：如果数据分布随机，跨越cache line的概率就会大大增加，导致性能降低；现代编译器实现中的堆栈对齐一部分是对cache的考量而不再是远古时期对dram的考量。

然而堆栈对齐更主要是为了保证simd的正常运行；simd使用的长数据在非对齐情况下更容易跨越cache line（avx512向量正好就是cache line大小），非对齐情况下编译器无法为simd生成对齐专用指令（movaps非对齐会直接硬件异常）；即使不用对齐专用指令，movups在对齐情况下的表现也更加稳健（其实仍然是cache-line问题）

其他类型处理器或旧处理器往往没那么宽松：Cortex-M允许拦截非对齐访问，而其他甚至可能在非对齐访问时直接硬件异常；良好的跨平台代码仍需要严格考虑对齐问题。

尽管大多数现代cpu的cache line是64 bytes， 部分cpu的数据总线或fpu宽度却只有32 bytes，avx512的运算会被拆成两个μop，所以速度与avx2差不了多少

我遇到的陷阱：为某个内存区域添加隐式header时（比如做slice）一不注意可能就会破坏对齐：

static uint8_t *_p;
#define $(T) (_p = &(uint8_t[sizeof(T)+4]){0}, do_sth_to_hdr(_p), (T*)(_p+4))
// 最后的偏移可能破坏对齐！

更好的作法应该是利用结构体自动对齐：

static void *_p;
#define $(T) (_p = &(struct{int rc; T v;}){0}, do_sth_to_hdr(_p), (T*)&_p->v)
