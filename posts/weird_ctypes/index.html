对于c类型系统的思考：不存在的类型，所有权与更多

2026-06-035 min read (2163 words)
目录

这学期有数据结构的课程，完成课程之余我会用c重写或实现一些其他类型；当一个泛型数据结构需要拷贝外部数据时，C（甚至C++）的实现中会遇到一些有趣的抉择。

拷贝外部数据对于c++倒没什么好说的：C++有模板做泛型支持，拷贝直接使用目标类型的拷贝构造或赋值重载，拷贝、移动与所有权问题后面再说；对于C，实现泛型的选项只有两个，要么使用void指针擦除类型，要么使用宏魔法；最简单的作法是约定调用者只能传入指针，生命周期由调用者负责。再高级点可以模拟oop的构造与析构函数实现自动生命周期管理。但如果我不想为每个类型手动实现构造/析构呢？？

一般实现的困难在于，调用者传入的复杂类型会退化成指针，无法分辨调用者是想用类型本身还是类型引用作为kv；那么我们就显式传入类型信息：

// 版本1
#define rb(key, value) \
struct { \
    rb_node *root; \
    size_t size; \
    cmp_t (*cmp)(void*, void*); \
    \
    key key_type; \
    value val_type; \
}

typedef struct rb_tree {
    rb_node *root;
    size_t size;
    cmp_t (*cmp)(void*, void*);
} rb_tree;

int main() {
    rb(str, int) tree = {
        .cmp = str_cmp,
    }; // 可以安全转型
    // 如果愿意放弃炫酷模板语法：
}

// 版本2
typedef struct rb_tree {
    rb_node *root;
    size_t size;
    cmp_t (*cmp)(void*, void*);
    size_t key_size, val_size;
}rb_tree;

#define rb(key, value, cmp_func) \
{.key_size = sizeof(key), .val_size = sizeof(value), .cmp = cmp_func}

int main() {
    rb_tree tree = rb(str, int, str_cmp); //获得更好的跨函数灵活性
}

有了这些类型信息我们可以做到不少有趣的事：sizeof信息可以用来判断需要拷贝多少字节，对于小于等于指针大小的数据（指针大小一般等于处理器位数大小）可以直接赋值，不用拷贝（但根据windows abi文档, 3、5、6、7字节的类型仍需要拷贝）；如要实现at接口，也可以用同样方法判断要返回void还是void**（当void直接承载value时）。对于版本1的实现，我们甚至能通过__typeof__()来实现更高级的功能（尽管该标准到c23才落实），比如foreach。版本1的缺点是传递给其他函数会丢失kv的类型。

如果注意到上述代码中写的是str而不是char *就会发现问题所在：字符串无法在这里实现拷贝！仔细一想，字符串“类型”根本不存在于c，却被当作标准一直使用着：char *对于c来说只是char类型的指针，而字符串语义是人们强加上去的，c类型系统从来不知道有这个东西存在，自然也就无法对其做其他类型的统一操作。而更深层次的问题是：c语言不存在动态大小的类型，即类型系统本身无法静态地表达大小这个信息，sizeof获得的大小也是事后分析得出的。所以为了做到这一点，必须在类型外表达大小信息。

即使是这样，我们仍能看到无法被绕过的天然缺陷：
假设我们定义str为：

typedef struct str {
    char *data;
    size_t size;
} str;

多出来的这一层嵌套仍然只能让前述的宏知道str类型本身，但无法知道要对这个类型做什么不同于其他类型的事（否则多一层嵌套仍等价于引用）。尽管在c中我们有几种别扭的类型逻辑判别方式，但都不是长久之计。但如果类型系统本身能提供.size()，就会变得容易得多。

接下来就是拷贝深度与移动问题：按照我们目前的c实现，没有任何办法自动解决这个问题；而在c++中也一样，只不过类型系统提供的拷贝构造能够让我们手动指定拷贝、移动方式。但再让我们仔细想想，这个问题为什么会存在？如果类型本身能表达拥有或借用，拷贝和移动就是能被自动决定的过程；c++可以通过显式delete拷贝、移动构造函数，从而实现相对安全的自动所有权语义。然而不经意的裸指针引用，隐式类型转换，以及并发环境能轻易破坏这个保障。

c/c++中的所有权问题和上述问题是同一模式的：裸指针的语义是“我不是所有者，我只是借用了资源，我不应该删除它”，但这只是约定，不是类型系统强制的。尽管有不少曲折的解决方案，c/c++类型系统本身无法静态地表达所有权信息，为了做到这一点，必须在类型外表达所有权信息。像Core Guidelines所述的owner<T*>泛型：它什么也不做，唯一的作用是供静态分析工具检测是否存在违反所有权模型，这反而成了保证所有权约定的终极手段。

更直接的说法是：类型系统缺乏表达某种信息的能力，为了使用这种信息，只能遵守某种约定，或在外部提供额外信息（约定又何尝不是外部信息呢？）。

在这之上我们能看到三种解决路径：

  1. 通过语言内的包装来保证约定
  2. 通过语言外的检查工具来保证约定
  3. 直接把需要的信息内置到语言中

rust走的正是第三条路线：直接把所有权烧进类型系统，让编译器来保证，彻底不依赖约定或工具。尽管这让编码过程变得痛苦，但毫无疑问这是正确的进步方向。反观一些c/c++库，他们往往需要大量代码来补偿类型系统或者语言本身的表达能力缺失：防御性代码、所有权管理代码、边界信息传递代码，这些导致顶尖大佬们严重脑损伤的防呆工作只是为了防止某个三流程序员不经意的小巧思 导致资本家巨额损失 （无意冒犯）

然而编程语言只是工具，当你因为无论什么原因只能使用某个工具来完成所有工作时，解决问题才是重点，而不是工具的选择。对于一开始发现的问题，我的解决方案是：数据结构的基本实现完全不管理生命周期。如果需要提供某个特定类型的特殊支持，直接包装一层或做个组合就好了，没必要病态地追求可复用性。此外就是，与其解决一个接口可能会出现的各种意外情况，不如从一开始就设计不容易用错的接口。如果所做的项目不是什么学校作业或者团队工作，那么dont give a shit，我自己爱做什么就做什么，在完全自由的情况下，灵机一动的小巧思（或愚蠢的主意）导致的灾难反而更能增长对项目设计的经验。
